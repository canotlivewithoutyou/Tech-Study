# WebSocket (웹소켓)

> **핵심:** 하나의 TCP 연결을 유지하면서 클라이언트와 서버가 실시간으로 양방향 통신할 수 있도록 하는 프로토콜

## 1. 웹소켓이란?

### 개념

- 클라이언트와 서버가 **하나의 TCP 연결을 지속적으로 유지**하며 양방향으로 데이터를 주고받는 통신 프로토콜
- 연결이 수립되면 클라이언트와 서버 모두 상대방의 요청 없이 메시지를 전송할 수 있음
- 채팅, 실시간 알림, 주식 시세, 온라인 게임 등 실시간성이 중요한 서비스에 활용

### HTTP와 WebSocket의 차이

| 구분     | HTTP               | WebSocket        |
| ------ | ------------------ | ---------------- |
| 통신 방식  | 요청 → 응답 중심         | 양방향 통신           |
| 데이터 전송 | 클라이언트 요청에 대한 응답    | 양쪽에서 언제든 전송      |
| 연결     | Keep-Alive로 재사용 가능 | 연결을 지속적으로 유지     |
| 오버헤드   | 요청·응답마다 HTTP 헤더 포함 | 연결 이후 가벼운 프레임 사용 |
| 주요 활용  | 일반적인 API, 웹페이지     | 채팅, 게임, 실시간 데이터  |

**예시: 실시간 채팅 서비스**

- HTTP Polling 방식
  - 클라이언트가 주기적으로 서버에 "새 메시지가 있나요?"라고 요청
  - 새 메시지가 없어도 불필요한 요청 발생
- WebSocket 방식
  - 처음 한 번 연결을 수립
  - 새로운 메시지가 발생하면 서버가 즉시 클라이언트에 전달
  - 반복적으로 새 메시지를 확인할 필요가 없음

→ **서버가 먼저 데이터를 전달할 수 있다는 점이 핵심적인 차이**

---

## 2. 웹소켓의 동작 과정

### ① 연결 요청 (Handshake)

- 웹소켓은 일반적으로 HTTP 요청으로 연결을 시작
- 클라이언트가 서버에 프로토콜 전환을 요청
- HTTP/1.1에서는 `Upgrade: websocket` 헤더 사용

### ② 프로토콜 전환

- 서버가 웹소켓 연결을 수락하면 `101 Switching Protocols` 응답
- HTTP에서 WebSocket 프로토콜로 전환

### ③ 양방향 데이터 통신

- 기존 TCP 연결을 그대로 유지
- HTTP 요청·응답 형식 대신 WebSocket 프레임으로 데이터 교환
- 클라이언트와 서버가 독립적으로 메시지를 전송할 수 있음

### ④ 연결 종료

- 통신이 끝나면 연결 종료
- 네트워크 장애 등으로 연결이 끊긴 경우 재연결 로직 필요

**전체 흐름**

`HTTP 연결 요청 → 101 응답 → WebSocket 연결 수립 → 양방향 메시지 교환 → 연결 종료`

**추가로 알아둘 점**

- `ws://` : 일반 웹소켓 연결
- `wss://` : TLS로 암호화된 웹소켓 연결
- HTTPS와 마찬가지로 실제 서비스에서는 보안을 위해 `wss://` 사용

## 3. 웹소켓의 특징 및 한계

### 장점

**① 실시간 양방향 통신**

- 클라이언트와 서버 모두 필요한 시점에 메시지 전송 가능
- 서버가 클라이언트의 요청을 기다리지 않아도 됨

**② 통신 오버헤드 감소**

- 연결 이후 매번 HTTP 헤더를 전송할 필요가 없음
- 메시지가 빈번하게 발생하는 환경에서 효율적

**③ 연결 재사용**

- 하나의 TCP 연결을 유지하며 여러 메시지를 주고받음
- 반복적인 통신에 적합

### 한계

**① 서버 자원 부담**

- 클라이언트와 서버가 지속적으로 연결된 상태를 유지
- 동시 접속자가 증가할수록 서버의 메모리와 커넥션 관리 부담 증가

**② 서버 확장 시 메시지 공유 문제**

- 서버가 여러 대라면 서로 다른 서버에 연결된 사용자 간 메시지 전달이 필요
- Redis Pub/Sub 같은 메시지 브로커를 활용할 수 있음

**예시: 채팅 서버가 2대인 경우**

- 사용자 A → 서버 1에 연결
- 사용자 B → 서버 2에 연결
- A가 메시지를 보내면 서버 1이 수신
- 서버 1은 사용자 B에게 직접 메시지를 전달할 수 없음
- Redis Pub/Sub 등을 통해 서버 2에 메시지를 전달하고, 서버 2가 사용자 B에게 전송

→ **WebSocket은 클라이언트와 서버 간 통신을 해결하지만, 서버 간 메시지 공유까지 자동으로 해결하지는 않음**

**③ 연결 끊김 및 재연결 처리**

- 네트워크 불안정, 서버 재시작 등으로 연결이 끊어질 수 있음
- 클라이언트에서 재연결 로직 구현 필요
- 연결이 끊어진 동안 누락된 메시지 처리도 고려해야 함

**④ 인증 및 보안**

- 연결 수립 시점에 사용자 인증 필요
- 장시간 연결을 유지하므로 토큰 만료와 권한 변경에 대한 처리 필요
- 연결 이후의 메시지에 대해서도 적절한 권한 검증 필요

## 4. WebSocket의 대안: SSE

### SSE(Server-Sent Events)란?

- 서버에서 클라이언트로 데이터를 지속적으로 전달하는 **단방향 통신 기술**
- HTTP 기반으로 동작
- 클라이언트에서 서버로 실시간 메시지를 보낼 필요가 없다면 비교적 간단하게 구현 가능

### WebSocket vs SSE

| 구분     | WebSocket      | SSE               |
| ------ | -------------- | ----------------- |
| 통신 방향  | 양방향            | 서버 → 클라이언트        |
| 기반 기술  | WebSocket 프로토콜 | HTTP              |
| 자동 재연결 | 별도 구현 필요       | EventSource 기본 지원 |
| 대표 사례  | 채팅, 온라인 게임     | 실시간 알림, 진행 상태 표시  |

### 어떤 상황에서 선택할까?

- **WebSocket**
  - 채팅처럼 클라이언트와 서버가 서로 실시간으로 메시지를 주고받아야 하는 경우
- **SSE**
  - 서버에서 클라이언트로만 실시간 데이터를 전달하면 되는 경우
  - 예: 작업 진행률 표시, 실시간 알림

---

## 5. 정리

- WebSocket은 하나의 TCP 연결을 유지하는 **실시간 양방향 통신 프로토콜**
- HTTP 핸드셰이크를 통해 연결을 수립한 뒤 WebSocket 프레임으로 데이터를 교환
- 통신 오버헤드를 줄일 수 있지만, **서버 자원 관리·확장성·재연결·인증**을 고려해야 함
- 단방향 데이터 전송만 필요하다면 SSE도 좋은 대안

**결론: 실시간 통신이 필요하다고 무조건 WebSocket을 사용하는 것이 아니라, 서비스에 필요한 통신 방향과 운영 복잡도를 고려해 적절한 기술을 선택해야 한다.**
