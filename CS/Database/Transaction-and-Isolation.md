# 트랜잭션과 격리 수준 (Transaction & Isolation Level)

## 1. 트랜잭션이란?

**트랜잭션(Transaction)**은 데이터베이스의 상태를 하나의 일관된 상태에서 다른 일관된 상태로 바꾸는 **논리적 작업 단위**다.

- 여러 SQL 문을 하나의 작업으로 묶는다.
- 작업을 더 이상 나눌 수 없는 단위로 취급한다.
- 모든 작업이 성공하면 `COMMIT`, 하나라도 실패하면 `ROLLBACK`한다.
- 핵심 원칙은 **All or Nothing**이다.

### 계좌 이체 예시

계좌 A에서 B로 10,000원을 이체하는 작업은 다음 단계로 구성될 수 있다.

1. A 계좌의 잔액을 확인한다.
2. A 계좌에서 10,000원을 차감한다.
3. B 계좌에 10,000원을 더한다.

2번까지만 성공하고 3번이 실패하면 돈이 사라진 것처럼 보인다. 따라서 세 작업을 하나의 트랜잭션으로 묶고, 중간에 오류가 발생하면 전체를 되돌려 데이터의 무결성을 지켜야 한다.

```text
BEGIN
  A 계좌 잔액 확인
  A 계좌 출금
  B 계좌 입금

  모두 성공 -> COMMIT
  하나라도 실패 -> ROLLBACK
END
```

## 2. 트랜잭션의 특성: ACID

| 특성 | 의미 | 핵심 질문 |
|---|---|---|
| **Atomicity (원자성)** | 트랜잭션의 연산이 모두 반영되거나 모두 취소된다. | 작업이 일부만 적용되지는 않는가? |
| **Consistency (일관성)** | 트랜잭션 전후에 제약 조건과 비즈니스 규칙을 만족하는 유효한 상태를 유지한다. | 데이터 규칙이 계속 지켜지는가? |
| **Isolation (격리성)** | 동시에 실행되는 트랜잭션이 서로의 중간 상태에 부적절하게 간섭하지 않는다. | 동시 실행 결과가 허용된 수준으로 분리되는가? |
| **Durability (지속성)** | 커밋된 결과는 장애가 발생해도 영구적으로 보존된다. | 완료한 결과가 사라지지 않는가? |

> 일관성은 데이터베이스만으로 자동 보장되는 성질이 아니다. 기본 키, 외래 키, `CHECK` 같은 제약 조건과 올바른 애플리케이션 로직이 함께 비즈니스 규칙을 지켜야 한다.

### ACID와 관련된 주요 장치

- **Undo Log**: 원자성과 롤백, MVCC를 지원한다.
- **Redo Log**: 커밋된 변경 사항의 지속성을 지원한다.
- **Lock**: 충돌하는 작업의 동시 실행을 제어한다.
- **Isolation Level**: 트랜잭션 사이에 어느 정도의 변경 내용을 공개할지 정한다.

## 3. TCL (Transaction Control Language)

TCL은 트랜잭션을 시작하고 확정하거나 되돌리는 명령어다.

| 명령어 | 역할 |
|---|---|
| `START TRANSACTION` 또는 `BEGIN` | 명시적으로 트랜잭션을 시작한다. |
| `COMMIT` | 현재 트랜잭션의 변경 사항을 영구 반영한다. |
| `ROLLBACK` | 현재 트랜잭션의 변경 사항을 전부 취소한다. |
| `SAVEPOINT name` | 트랜잭션 안에 중간 지점을 만든다. |
| `ROLLBACK TO SAVEPOINT name` | 해당 저장점 이후의 작업만 취소한다. |
| `RELEASE SAVEPOINT name` | 저장점을 제거한다. |

### 기본 처리 흐름

```sql
START TRANSACTION;

UPDATE account
SET balance = balance - 10000
WHERE account_id = 1;

UPDATE account
SET balance = balance + 10000
WHERE account_id = 2;

COMMIT;
```

오류가 발생했다면 `COMMIT` 대신 `ROLLBACK`한다.

### Savepoint로 부분 롤백하기

```sql
START TRANSACTION;

UPDATE orders
SET status = 'PAID'
WHERE order_id = 100;

SAVEPOINT payment_done;

INSERT INTO delivery (order_id, address)
VALUES (100, 'Seoul');

ROLLBACK TO SAVEPOINT payment_done;
COMMIT;
```

`ROLLBACK TO SAVEPOINT`는 저장점 이후의 작업만 되돌린다. 반면 인자 없는 `ROLLBACK`은 트랜잭션 전체를 취소한다.

> MySQL은 기본적으로 `autocommit`이 활성화되어 있어 명시적 트랜잭션 밖의 각 SQL 문을 즉시 커밋한다. 또한 일부 DDL은 암묵적 커밋을 일으킬 수 있으므로 트랜잭션 안에서 DDL과 DML을 섞을 때 주의해야 한다.

## 4. 동시 실행 시 발생할 수 있는 이상 현상

| 현상 | 설명 | 간단한 예시 |
|---|---|---|
| **Dirty Read** | 다른 트랜잭션이 아직 커밋하지 않은 값을 읽는다. | T1의 수정 값을 T2가 읽은 뒤 T1이 롤백한다. |
| **Non-Repeatable Read** | 한 트랜잭션에서 같은 행을 두 번 읽었는데 값이 달라진다. | 두 조회 사이에 다른 트랜잭션이 해당 행을 수정하고 커밋한다. |
| **Phantom Read** | 같은 범위 조건으로 다시 조회했을 때 행의 집합이 달라진다. | 두 조회 사이에 다른 트랜잭션이 조건에 맞는 행을 삽입한다. |
| **Lost Update** | 두 트랜잭션의 갱신 중 하나가 다른 갱신을 덮어써 사라진다. | 두 작업이 같은 초기 잔액을 읽고 각각 계산한 값으로 저장한다. |

`Non-Repeatable Read`는 **기존 행의 값 변화**, `Phantom Read`는 **조건에 맞는 행 집합의 변화**에 초점을 둔다.

## 5. 트랜잭션 격리 수준

격리 수준은 동시성과 데이터 일관성 사이의 균형을 정한다. 일반적으로 격리 수준이 높을수록 허용되는 이상 현상은 줄지만 잠금 대기와 충돌 가능성은 커질 수 있다.

### SQL 표준 기준

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read | 특징 |
|---|:---:|:---:|:---:|---|
| `READ UNCOMMITTED` | 가능 | 가능 | 가능 | 커밋되지 않은 변경도 읽을 수 있다. |
| `READ COMMITTED` | 방지 | 가능 | 가능 | 각 SQL 문은 실행 시점에 커밋된 데이터만 읽는다. |
| `REPEATABLE READ` | 방지 | 방지 | 표준상 가능 | 트랜잭션 안에서 같은 행을 반복 조회할 때 같은 값을 보장한다. |
| `SERIALIZABLE` | 방지 | 방지 | 방지 | 직렬 실행과 동등한 결과를 목표로 하는 가장 엄격한 수준이다. |

### MySQL InnoDB에서의 해석

- 기본 격리 수준은 `REPEATABLE READ`다.
- 일반 `SELECT`인 **일관 읽기(Consistent Read)**는 MVCC 스냅샷을 사용한다.
- InnoDB의 `REPEATABLE READ`에서는 같은 스냅샷을 사용하는 반복 조회가 일반적으로 Phantom Read를 보지 않는다.
- `SELECT ... FOR SHARE`, `SELECT ... FOR UPDATE`, `UPDATE`, `DELETE` 같은 **잠금 읽기/현재 읽기**는 최신 데이터를 읽으며, 범위 조건에서는 Next-Key Lock으로 팬텀 삽입을 막는다.

따라서 격리 수준 표만 외우기보다 **사용 중인 DBMS, 읽기 방식, 인덱스와 쿼리 조건**을 함께 확인해야 한다.

### 격리 수준 확인 및 변경

```sql
-- 현재 세션의 격리 수준 확인
SELECT @@transaction_isolation;

-- 다음 트랜잭션부터 현재 세션에 적용
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

격리 수준은 워크로드 전체에 일괄 적용하기보다, 데이터 정합성 요구와 충돌 비용을 측정한 뒤 선택한다.

## 6. 교착상태 (Deadlock)

교착상태는 둘 이상의 트랜잭션이 서로 보유한 잠금을 기다리며 누구도 진행하지 못하는 순환 대기 상태다.

```text
T1: row A 잠금 획득 -> row B 잠금 대기
T2: row B 잠금 획득 -> row A 잠금 대기
```

InnoDB는 대기 관계의 순환을 감지하면 트랜잭션 하나를 희생자(victim)로 선택해 롤백하고 오류를 반환한다. 교착상태는 완전히 제거하기 어려우므로 애플리케이션은 해당 트랜잭션을 **처음부터 재시도**할 수 있어야 한다.

### 교착상태를 줄이는 방법

1. **자원 접근 순서를 통일한다.**
   - 모든 트랜잭션이 테이블과 행을 같은 순서로 잠그게 한다.
2. **트랜잭션을 짧게 유지한다.**
   - 트랜잭션 안에서 외부 API 호출이나 사용자 입력을 기다리지 않는다.
3. **적절한 인덱스를 사용한다.**
   - 불필요하게 넓은 범위를 스캔하고 잠그지 않게 한다.
4. **한 번에 처리하는 범위를 줄인다.**
   - 대량 변경은 상황에 따라 작은 배치로 나눈다.
5. **잠금 대기 시간을 제한한다.**
   - 무한 대기 대신 타임아웃 후 실패 처리와 재시도 전략을 사용한다.

> Lock Timeout은 긴 대기를 끝내는 안전장치지만, 교착상태의 근본 원인을 제거하는 방법은 아니다.

## 7. 성능과 설계 체크리스트

- 트랜잭션 범위는 정합성을 지킬 수 있는 최소 단위로 잡았는가?
- 모든 성공 경로에서 `COMMIT`, 실패 경로에서 `ROLLBACK`되는가?
- 교착상태 및 일시적 잠금 오류에 대한 재시도 정책이 있는가?
- 업무 요구보다 지나치게 높은 격리 수준을 사용하고 있지 않은가?
- 조회와 수정 조건에 적절한 인덱스가 있는가?
- 트랜잭션 내부에 오래 걸리는 네트워크 작업이 포함되어 있지 않은가?

## 핵심 정리

- 트랜잭션은 여러 SQL 문을 하나로 묶는 **논리적 작업 단위**다.
- 성공하면 `COMMIT`, 실패하면 `ROLLBACK`한다.
- ACID는 **원자성, 일관성, 격리성, 지속성**이다.
- 격리 수준은 정합성과 동시성의 균형을 결정한다.
- InnoDB에서는 격리 수준뿐 아니라 **MVCC 읽기인지 잠금 읽기인지**도 함께 봐야 한다.
- 교착상태는 예방 노력과 함께 **감지 후 재시도**까지 설계해야 한다.
