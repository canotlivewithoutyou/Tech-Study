# Redis란? 상품 페이지를 예로 알아보는 캐시와 만료 시간

![Redis](./imgs/redis.png)

- **상황** — 여러 사용자가 같은 상품 페이지를 조회. 상품명과 설명이 그대로여도 요청마다 원본 데이터베이스(DB)에서 같은 정보를 읽으면 조회가 반복됨.
- **캐시 활용** — 한 번 읽은 상품 정보를 잠시 보관하고 다음 요청에 재사용해 DB 조회 횟수를 줄임. 이때 자주 쓰는 저장소가 **Redis(레디스)**.

## 1. Redis의 데이터 저장 방식

- **키-값 저장소** — Redis는 데이터를 주로 **메모리(RAM)**에 보관. 키는 데이터를 찾는 이름이고, 값은 해당 키로 꺼내는 내용.
- **상품명 예시** — `product:42:name`이라는 키에 `무향 핸드크림`을 저장. 상품 번호 42의 이름이 필요할 때 해당 키로 값을 조회.
- **활용 사례** — 메모리에서 값을 빠르게 읽을 수 있어 **캐시**로 자주 사용. 캐시는 한 번 구한 결과를 다음 요청에 재사용하기 위해 보관한 사본. Redis에는 로그인 세션이나 게임 순위도 저장 가능.

## 2. 상품 페이지 조회 흐름

상품 정보의 원본은 DB에 저장하고, 애플리케이션 코드에서 Redis를 먼저 조회하도록 구성.

| 요청 | 캐시 상태 | 서버의 처리 |
| --- | --- | --- |
| 첫 요청 | **캐시 미스** — 해당 키에 값이 없음 | 원본 DB에서 상품 정보를 읽어 Redis에 저장하고 응답 |
| 다음 요청 | **캐시 히트** — 같은 키에 값이 남아 있음 | Redis에서 읽은 상품 정보로 바로 응답 |

인기 상품을 천 명이 연달아 조회해도 캐시에 설명이 남아 있는 동안에는 같은 설명을 읽기 위한 DB 조회를 줄일 수 있음.

## 3. TTL과 상품명 변경

- **TTL(Time To Live)** — 키의 남은 유효 시간.
- **설정 예시** — 아래 명령의 `EX 300`은 상품명을 저장하면서 만료 시간을 **300초(5분)**로 설정한다는 뜻.

```text
SET product:42:name "무향 핸드크림" EX 300
```

- **만료 후 조회** — 5분이 지나 키가 만료되면 다음 요청에서 캐시 미스 발생. 서버는 원본 DB에서 현재 상품명을 읽어 캐시를 다시 채움.
- **만료 전 변경** — 저장한 지 1분 뒤에 DB의 상품명이 바뀌면 남은 4분 동안은 캐시에서 예전 이름을 읽을 수 있음.
- **즉시 반영이 필요한 경우** — 상품을 수정할 때 해당 캐시 키도 함께 삭제하거나 새 상품명으로 갱신.

## 4. 문자열 외에 활용할 수 있는 자료형

### Hash — 사용자 프로필

- 하나의 프로필에 `nickname`, `email`처럼 이름이 있는 필드를 여러 개 저장.
- 닉네임만 자주 바뀌는 경우 해당 필드만 수정하거나 조회 가능.
- 아래 예시에서 `HSET`은 닉네임을 `봄날`로 저장하고, `HGET`은 저장한 닉네임을 조회.

```text
HSET user:42 nickname "봄날"
HGET user:42 nickname
```

### Sorted Set — 게임 순위와 최근 본 상품

- **게임 순위** — 플레이어마다 점수를 부여하고 점수 순으로 순위를 조회.
- **최근 본 상품** — 상품마다 마지막으로 본 시각을 점수로 저장. 같은 상품을 다시 보면 해당 상품의 점수만 새 시각으로 갱신. 점수가 높은 순서로 조회하면 가장 최근에 본 상품이 맨 앞에 표시됨.

## 5. 빅 키와 핫 키

| 구분 | 의미 | 상품 페이지 예시 |
| --- | --- | --- |
| **빅 키(Big Key)** | 한 키에 담긴 값이 지나치게 크거나 원소가 많은 경우 | 상품 목록 전체를 문자열 하나로 저장하면 상품 하나를 보여줄 때도 전체 목록을 전송해 시간과 대역폭을 소모 |
| **핫 키(Hot Key)** | 특정 키에 조회 요청이 집중되는 경우 | 행사 상품의 이름처럼 짧은 값도 많은 사용자가 동시에 조회하면 핫 키가 될 수 있음 |

**핫 키가 만료될 때의 흐름**

1. 행사 상품의 캐시 키가 만료되어 첫 요청에서 캐시 미스 발생.
2. 첫 요청이 DB에서 값을 읽어 캐시를 다시 채우는 사이, 뒤따르는 요청들도 같은 키에서 캐시 미스를 겪어 DB 조회가 한꺼번에 몰릴 수 있음.
3. 트래픽이 몰릴 상품은 캐시를 만료 전에 미리 갱신해 DB 조회 집중을 줄일 수 있음.

## 캐시를 설계할 때 확인할 두 가지

- **화면 하나를 그리는 데 어떤 값이 필요한가?** → 한 키에 담을 데이터의 범위를 결정.
- **그 값이 몇 초 전 정보여도 괜찮은가?** → 허용할 수 있는 시간에 맞춰 TTL을 결정.
